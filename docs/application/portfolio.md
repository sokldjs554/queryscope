## 개발 배경

검색 실패를 수정할 때에는 원인 진단과 변경의 영향 범위를 함께 확인해야 합니다. 검색 결과가 없더라도 표기 차이, 형태소 분해, 복합어 처리에 따라 필요한 수정이 다릅니다. 또한 동의어와 분석기 규칙은 여러 질의에 함께 적용되므로, 한 질의를 개선한 변경이 다른 질의의 검색 순위나 정확도를 낮출 수 있습니다. 이 프로젝트의 목표는 수정안을 제안하는 단계부터 적용 여부를 판단하는 단계까지 재현 가능한 절차로 연결하는 것입니다.

이를 위해 형태소·검색 결과·운영 지식을 함께 제공해 LLM이 원인과 후보를 제안하도록 하고, 인용 근거 검사와 실제 검색 평가를 분리했습니다. 원문을 인용했다는 사실만으로 처방의 효과가 입증되지는 않기 때문입니다. 후보를 검색 엔진 사본에 적용한 뒤 목표 질의의 개선, 다른 질의의 성능 저하, 전체 평균 변화를 확인해 채택 여부를 결정합니다.

상품 카탈로그 72건과 기존 평가 질의 36건은 직접 작성했습니다. 이번에는 문자열이 중복되지 않는 새 24개 질의를 추가하고, 정답과 기준을 실행 전에 고정했습니다. 같은 상품·어휘와 기존 실패 지식을 재사용했으므로 완전한 독립 평가셋은 아닙니다. 실제 고객 로그에서 발견한 문제나 알바천국의 검색 성능을 검증한 프로젝트도 아닙니다.

## 개발 범위

서비스 방향·검증 범위를 정하고 Codex를 활용해 진행한 개인 프로젝트입니다. 코드 작성·수정, 실험 자동화, 문서 정리에 Codex의 지원을 받았습니다.

ko-search-clinic의 main이 아닌 RAG 서비스와 검증을 포함한 PR #2의 최신 커밋 `493935f6`에서 새 저장소로 이어받았습니다. 전체 Git 이력과 기준 태그 `upstream-pr2`를 보존하고 기존 저장소는 변경하지 않았습니다. 기존 검색 엔진·회귀 게이트·실제 API 24회 응답을 유지하면서 새 평가 분리, 수동 수정 후보, 설명 평가 기준, 데모와 운영 검증을 보완했습니다.

BM25와 GPT-5.4-mini를 사용한 실제 생성 실험은 PR #2의 과거 기록입니다. QueryScope의 새 실험에서는 추가 유료 API를 호출하지 않았습니다. 과거 Claude·임베딩·Elasticsearch 실험도 별도 보존 문서로 구분합니다.

## 검색 진단

질의와 관찰 내용을 입력하면 형태소, 검색 상위 결과, 관련 운영 문서를 모읍니다. 운영 지식 상위 3개를 모델에 제공하고 설명·실패 유형·인용·수정 후보를 구조화된 응답으로 받습니다. 평가용 정답표는 생성 입력에 넣지 않습니다.

문서는 프로젝트에서 작성한 운영 지식입니다. 문서 ID와 본문을 대조하고, 연속 공백·줄바꿈과 짝이 맞는 강조 기호의 차이는 비교용으로 정리한 뒤 원문 위치에 대응합니다. 단어 경계와 문장부호를 바꾼 인용, 없는 출처, 잘못된 수정 규칙은 적용 경로에서 차단합니다. 인용이 맞더라도 설명의 의미적 타당성이 자동으로 보장되는 것은 아닙니다. 원인 분류·인용 추적·의미적 지지·수정 구조·수정 효과를 나눈 평가 기준을 만들었고, 자동 확정할 수 없는 의미 판단은 `requires_human_review`로 표시합니다. 기존 24개 응답의 독립 인간 의미 평가는 아직 수행하지 않았습니다.

## 수정안 검증

동의어 연결, 사용자 사전 등록, 복합어 분해를 수정 후보로 다룹니다. Pydantic 검사 후 기존 36개 질의를 다시 평가합니다. 표적 질의의 nDCG 개선, 다른 질의의 nDCG·정밀도·재현율 저하, 전체 평균 nDCG 변화를 함께 확인하고 통과한 후보만 별도 세션에 적용합니다. 이 기준은 작성한 평가셋 안에서의 적용 조건이며, 평가셋 밖의 무회귀를 보장하지 않습니다.

**PR #2의 과거 실제 응답:** 사후 재검증한 후보 6건 가운데 4건은 채택되고 2건은 기각됐습니다. ‘아답터’와 ‘백팩’은 사용자 사전에 등록하는 것만으로 검색이 개선되지 않아 반영하지 않았습니다. 각 후보는 새 세션에서 검사했으며 누적 성능 수치가 아닙니다.

| 질의 | 검색 순위 점수 전 → 후 (nDCG) | 판정 |
|---|---|---|
| 도너츠 | 0 → 1.0000 | 채택 |
| 블루투스 스피커 | 0.5000 → 1.0000 | 채택 |
| 핸드폰 | 0 → 0.5364 | 채택 |
| 케잌 주문 | 0 → 1.0000 | 채택 |
| 아답터 / 백팩 | 각각 0 → 0 | 기각 |

nDCG는 관련 상품이 검색 결과의 앞쪽에 나오는지를 평가하는 지표입니다. 이 평가에서는 1에 가까울수록 좋으며, 위 수치는 각 질의의 개별 결과입니다.

**QueryScope에서 추가로 검증한 수동 후보:** 아답터·백팩은 사전 등록만으로 카탈로그의 어댑터·배낭 표현과 연결되지 않았습니다. 운영자가 지정한 표준형 연결을 함께 적용해 두 질의가 각각 0에서 1로 개선됐고, 각 후보는 기존 36질의 게이트를 통과했습니다. 두 후보를 함께 적용한 기존 36질의 평균은 0.5839에서 0.6395로 바뀌었습니다. 모델이 새 수정안을 발견한 성과로 계산하지 않습니다.

잘못된 `[티슈, 티슈]` 복합어 원후보는 계속 차단했습니다. 별도의 수동 후보인 물티슈→물+티슈는 0에서 1로 개선됐고 기존 게이트를 통과했지만, 아래 신규 20질의의 결합 설정에는 포함하지 않았습니다. 백팩의 원인 분류 오류, 원문 어미를 바꾼 인용, 문서 제목을 본문처럼 인용한 사례도 미해결 기록으로 남겼습니다. 운영 지식의 NR 품사 제거 설명은 실제 코드와 달라 IC/NR을 구분하도록 수정했습니다.

## 실험과 결과

**기존 실제 생성 실험:** API 호출 전에 12개 사례와 문서 제공·제거 조건을 고정했습니다. 질의와 함께 표기 차이·분석 오류 등 원인에 대한 힌트를 포함한 관찰 문장을 제공했으므로, 원인 정보가 없는 실제 문의를 스스로 진단한 정확도로 해석할 수 없습니다. 총 24회 호출의 응답을 확보했고, 토큰 사용량 기준 추정 비용은 약 $0.03이었습니다. 정확한 토큰·비용 내역은 원시 기록에 보존했습니다. API 지연 중앙값은 1.39초, p95는 2.67초였습니다. 검색·회귀 검사까지 포함한 전체 응답 시간은 아닙니다.

최초에는 24건 중 12건이 검증에서 차단됐습니다. 표시 형식 차이까지 오류로 처리한 부분을 보완한 뒤 같은 저장 응답을 재검증했고, 인용·형식 통과 6건·보류 12건·차단 6건을 확인했습니다. 인용·형식 검사를 통과해도 검색 개선은 그다음 회귀 검사로 별도 판정합니다.

이는 모델을 재학습하거나 새로운 평가셋에서 확인한 성능 개선이 아닙니다. 실패를 본 뒤 검증기를 보완한 사후 결과로, 최초 결과·원시 응답·보완 후 결과를 모두 보존했습니다. 문서를 제거한 12건에서는 10건이 보류되고 2건이 출처 문제로 차단됐으며 적용된 수정은 없었습니다.

**새 오프라인 평가:** 24개 질의·정답·평가 기준을 실행 전 커밋 `4be6122`와 SHA-256으로 고정했습니다. 관련 문서가 있는 20개에서 아답터·백팩의 두 수정안을 함께 적용한 평균 nDCG@10은 **0.8255→0.9142**였습니다. 4개 질의가 개선됐고 nDCG@10·recall@10·고정 분모 P@5 하락은 없었습니다. 나머지 4개는 관련 문서가 없어 순위 평균에서 제외했고 전후 모두 검색 결과가 없었습니다. 이를 모델의 보류 성공으로 계산하지 않았습니다.

| 신규 질의 | nDCG@10 전 → 후 |
|---|---|
| 여행용 아답터 / 노트북 아답터 | 각각 0.6309 → 1 |
| 방수 백팩 / 종주 백팩 | 0.3333 → 1 / 0.6309 → 1 |
| 거실 카페트 | 0.8262 → 0.8262 |
| 초콜렛 선물 | 0.4582 → 0.4582 |
| 워시 | 0 → 0 |

**원인 힌트 유무 비교:** 질의·검색기·문서 수를 유지하고 관찰 문장만 바꿨습니다. 신규 원인 계열 11개 질의의 근거 hit@3는 힌트 조건 11/11, 무힌트 조건 1/11이었습니다. 기존 개발 사례 9개에서는 각각 8/9와 6/9였으며 새 결과와 분리했습니다. 힌트 조건에는 원인 방향이 드러나므로 이 차이는 입력 힌트 의존도를 보여 줍니다. 낮은 결과를 확인한 뒤 이 평가셋에 맞춰 검색기를 튜닝하지 않았습니다.

이 비교는 문서 검색 평가입니다. 새 LLM을 호출하지 않았으므로 새 질의의 원인 진단 정확도, 의미적 설명 타당성, 자료 부족 시 자연 발생 보류율은 미실행으로 표시했습니다. 작성한 테스트 응답으로 확인한 보류 규칙을 실제 모델 성능으로 집계하지 않았습니다.

## 사용 화면

[공개 저장 결과 데모](https://queryscope-zwia.onrender.com/)에서 A04 ‘핸드폰’을 선택하면 검색 관측 → 인용 원문 → 수정안 채택 결과를 확인할 수 있습니다. A01은 인용 검증에서 차단된 사례입니다. 기록은 JSON으로 내려받을 수 있습니다. [새 평가 비교](https://queryscope-zwia.onrender.com/evaluation.html)는 신규 24질의의 전후 결과와 힌트 유무별 입력·검색 문서를 표시합니다.

공개 사이트는 저장된 응답과 오프라인 결과를 재생하는 정적 데모입니다. 새 모델 응답을 생성하지 않으며 생성 서버나 API 키를 배포하지 않았습니다. Render는 검증 코드 `714600f`의 배포 상태를 `live`로 보고했습니다. 검증 환경의 네트워크 제한으로 공개 주소의 실제 HTTP·브라우저 접속은 확인하지 못했습니다. [로컬 실행 방법](https://github.com/sokldjs554/queryscope#데모-실행)도 제공합니다.

로컬 브라우저에서는 1440·320·390·650px에서 저장 응답 24건과 신규 평가 24행, 입력 비교, 가로 넘침, 이전 진단 무효화, 취소·오류·다운로드를 검사했습니다. 새 생성 경로의 상태 전환에는 테스트 응답을 사용했습니다.

최종 로컬 테스트는 **353개 통과·1개 건너뜀·2개 제외**입니다. 검증 코드 `714600f`의 [Ubuntu·Windows 테스트 및 검색 품질 CI](https://github.com/sokldjs554/queryscope/actions/runs/40480583240)도 모두 통과했습니다. 수정 후 오프라인 평가를 재실행해 최초 결과와 일치함을 확인했습니다.

## 운영 설정과 한계

실제 생성은 서버에서 명시적으로 활성화하고 로컬 운영 토큰으로 접근합니다. API 키는 화면에 전달하지 않습니다. 요청 전에 비용을 예약하며 자동 재시도 없이 호출 수를 제한합니다. 요청·보류·차단·상류 오류·바쁨 응답과 최근 100회의 p95를 확인할 수 있습니다. 기존 승인 24회는 소진됐으므로 기본 호출 한도를 0으로 설정하고 종료된 유료 평가 실행 경로를 차단했습니다. QueryScope의 추가 유료 호출은 0회입니다.

실제 로컬 HTTP 검사에서 준비 이후 정적 자료·상태 조회 GET 120회는 모두 200이었고 p95는 1.937ms였습니다. 기본 생성 경로의 예상 503과 빈 입력의 422도 확인했습니다. 이 수치는 모델 추론이나 검색 계산의 지연, 공개 서비스의 SLA가 아닙니다. 오류·동시 요청·취소의 로컬 테스트도 실제 공급자 장애 실험과 구분합니다.

확인한 범위는 작성 자료의 검색 평가, 로컬 서비스·화면, CI와 Render의 정적 배포 상태입니다. 실고객 효과, 공개 생성 API의 장기 운영, 다중 서버의 집계·인증, 독립 평가셋의 일반화는 확인하지 않았습니다. 모델 학습, LangChain·LlamaIndex 사용 경험으로 소개하지 않습니다.

남은 과제는 무힌트 근거 검색, 미해결 순위 사례, 독립적인 사람의 의미 평가, 새로운 질의에서의 실제 모델 진단·보류 성능입니다. 후속 검색 개선에 현재 새 평가셋을 사용한다면 이를 개발셋으로 전환하고 또 다른 평가셋을 고정해야 합니다. 추가 생성 평가의 모델·호출 수·비용 계획은 별도로 작성했으며 승인이나 실행을 완료한 것으로 표시하지 않습니다.
