# 윤기혁 자기소개서

지원 기업: (주)미디어윌네트웍스 · 알바천국 AI 개발자

## 지원동기

알바천국의 AI 공고 비교 분석과 입사지원 메시지 작성 서비스에서 주목한 부분은, 공고와 이력서의 정보를 바탕으로 사용자의 판단과 지원에 쓰이는 내용을 생성한다는 점입니다. 공고 비교에서는 급여·근무시간 같은 조건이 정확히 대응해야 하고, 지원 메시지에서는 이력서에 없는 경험이 추가되지 않아야 한다고 생각합니다. 문장의 자연스러움과 함께 원문 정보의 누락·왜곡을 평가하는 기준이 필요합니다.

저는 한국어 검색 진단 프로젝트 QueryScope에서 LLM의 설명을 원문과 대조하고, 제안한 수정이 실제 검색을 개선하는지 검사했습니다. 인용 조건을 통과한 답변도 수정 효과가 없거나, 색인에 없는 표현을 연결 대상으로 제안할 수 있었습니다. 이 경험을 통해 생성 결과를 실제 기능에 연결할 때 필요한 검증을 더 깊이 다루고 싶어졌습니다. 공고에 명시된 RAG 개발과 실험·평가, 운영 품질 개선 업무에서 경험을 발전시키며 알바천국의 AI 기능 개발에 기여하고자 지원했습니다.

## 직무역량

서비스 방향과 평가 범위를 정하고, 코드 구현·실험 자동화·문서 정리에 Codex의 지원을 받았습니다. Python·FastAPI 기반 진단 API와 점검 화면에 형태소 분석 결과, 검색 순위, 관련 운영 문서를 연결했습니다. 수정 후보는 동의어 연결·사용자 사전 등록·복합어 분해로 제한하고, 원인 설명·원문 인용·수정 효과를 따로 평가했습니다.

아답터와 백팩은 사용자 사전 등록만으로 개선되지 않아 카탈로그의 어댑터·배낭과 연결했습니다. 두 수동 후보는 각각 nDCG@10이 0에서 1로 개선됐습니다. 후속 수정까지 적용한 개발 20질의의 평균은 0.9142에서 0.9992로 높아졌지만, 별도 작성한 자료의 18질의 평균은 0.5351로 그대로였습니다. 특정 표현에 맞춘 사전 수정의 효과를 새로운 표현에 대응하는 능력으로 확대하지 않고 기록했습니다.

후속 단계에서는 이미 살펴본 평가 자료를 개발용으로 전환했습니다. 검색 결과가 0건일 때 요청 설명과 상품 설명에서 일반적인 안내 문구를 제외한 단서가 둘 이상 겹치면 후보를 찾도록 보완했습니다. 영어 microscope 질의에도 현미경 후보를 보여 주되, 이를 동의어가 확인된 사실로 처리하지 않았습니다. 같은 개발 자료의 무힌트 원칙 검색은 8개 중 7개에서 8개로 바뀌었습니다. 모델 진단 정확도와 구분해 설명할 수 있도록 입력과 측정 범위를 함께 남겼습니다.

## 문제 해결 경험

검증 과정에서는 답변의 내용뿐 아니라 검사 기준의 오류도 살폈습니다. 기존 응답에서 원문 표현을 바꾼 인용과 줄바꿈·강조 표시만 다른 인용이 함께 차단되는 문제를 발견했습니다. 단어 경계와 문장부호를 보존하면서 표시 차이만 정리하고, 일치 구간을 원문 위치에 연결했습니다. 같은 저장 응답을 다시 검사한 결과로 기록해 새 모델의 성능 향상과 구분했습니다.

이후 같은 모델 스냅샷으로 기존 12사례의 실제 24응답을 확보했습니다. 8응답은 상품 ID를 운영 지식의 인용 출처로 사용해 차단됐고, 정상이라고 설명하면서 상태를 supported로 반환한 사례도 있었습니다. microscope에는 색인에 없는 대표어를 제안했습니다. 원응답은 보존하고 출처 구분과 대표어·복합어 대상 검사를 보완했습니다.

변경 후에는 같은 12사례의 직접 비교 24회와 추가 12사례의 24회를 나누어 실제 생성했습니다. 직접 비교에서 차단은 8건에서 4건으로, 보류·무패치·검증 통과 계약을 충족한 응답은 12건 중 8건에서 11건으로 바뀌었습니다. 새 48응답 중 효과를 측정한 8후보는 7응답이 채택되고 1응답이 기각됐습니다. 채택된 응답은 서로 다른 질의로 5개이며, 같은 사례를 두 조건에서 실행한 결과를 별도 문제 해결 수로 중복 계산하지 않았습니다.

남은 실패도 함께 기록했습니다. microscope는 무힌트에서 보류했고 힌트에서는 여러 단어로 된 대표어의 형식 오류로 차단됐습니다. 박자기는 무힌트에서 의미 대응을 확정하지 않았지만, 힌트에서는 다시 박자와 연결해 검색이 개선되지 않았습니다. 입력과 검사 규칙을 함께 바꾼 개발 결과이므로 개별 변경의 효과나 새 상품에 대한 진단 정확도로 확대하지 않았습니다.

기존 24응답은 원인 근거·원문 인용·의미적 지지·수정안·보류의 다섯 축으로 AI 판정과 이유를 남겼습니다. AI 검토는 사람의 독립 평가가 아니며 새 48응답의 의미 평가로도 계산하지 않았습니다. 좋은 수치와 함께 실패 원인, 아직 확인하지 못한 부분을 드러내는 것이 다음 개선의 출발점이라고 생각합니다.

## 입사 후 포부

입사 후에는 팀의 AI 기능별 입력 자료와 출력 형식, 기존 평가 기준을 먼저 익히겠습니다. 공고 비교나 지원 문구 생성 업무를 맡는다면 원문에 없는 정보의 추가, 주요 조건의 누락, 조건 간 잘못된 대응을 구분한 평가 사례를 팀과 함께 정리하겠습니다. 인용이 일치하는지와 문맥상 의미가 맞는지를 나누어 살피고, 사람이 판단해야 하는 부분의 기준도 실제 사례로 다듬겠습니다.

개선안을 적용할 때에는 기존 사례와 새로 확보한 사례를 구분해 비교하고, 품질 변화와 함께 응답 시간·실패율·호출 비용을 확인하겠습니다. 오류를 입력 자료, 검색, 생성, 후처리 단계로 나눠 추적하고 실험 조건과 수정 이유를 코드 리뷰로 공유하겠습니다. 변경 효과를 설명하고 반복해서 검증할 수 있는 개발자로 기여하겠습니다.
