## 1. 무힌트 근거 검색

기존 경로는 `query + problem`만 BM25에 전달해 실제 형태소/버려진 품사/상품 원문을 검색에 쓰지 않았다. 긴 문서도 처음 400자만 제공했다. 새 경로는 카탈로그에서 관측한 토큰 분해, 원문 부분어와 색인 토큰의 차이, 자모 유사 표기, 문자 체계의 차이로 검색 질의를 보강한다. 서로 다른 관측 신호의 문서를 우선 확보하고, 관련 부분을 최대 400자의 연속 원문으로 발췌해 위치와 전체 본문 해시를 남긴다.

검색기에는 정답·계열 라벨을 전달하지 않는다. 자모 유사도 .65 등은 개발 자료에서 정한 휴리스틱이며, 유사한 표기가 동의어라는 뜻은 아니다. 모델에는 검색용 원인 키워드 대신 실제 관측과 문서를 전달하고 그 입력도 별도 저장한다.

| 자료 | 힌트 기존 → 보완 hit@3 | 무힌트 기존 → 보완 hit@3 | 무힌트 MRR@3 기존 → 보완 |
|---|---|---|---|
| v1 개발 11개 계열 가설 | 11/11 → 11/11 | **1/11 → 10/11** | 0.0303 → 0.8636 |
| 새 자료 15개 계열 가설 | 9/15 → 11/15 | **6/15 → 10/15** | 0.2000 → 0.6000 |

| 새 자료의 계열 가설 | 수 | 무힌트 기존 → 보완 | 힌트 기존 → 보완 |
|---|---:|---|---|
| 표기 변형 | 3 | 3/3 → 3/3 | 3/3 → 3/3 |
| 영한 혼용 | 3 | 0/3 → 3/3 | 0/3 → 3/3 |
| 유의어 | 3 | **3/3 → 2/3** | **3/3 → 2/3** |
| 잘못된 분해 | 3 | **0/3 → 0/3** | **0/3 → 0/3** |
| 복합어 | 3 | 0/3 → 2/3 | 3/3 → 3/3 |

계열별 일반 원칙 문서가 상위3개에 있으면 적중이다. 관련 문서 목록은 실행 전에 고정했고 두 조건에 같은 기준을 썼다. 문서의 의미적 지지나 실제 원인 정확도 점수는 아니다. 모든 입력·신호·검색 문서·발췌가 원자료에 있다.

### 낮아진 결과와 가설 오류

- **V09 휴대용 배터리:** 양 조건 모두 적중→실패. 정상적인 휴대용→휴대 분석을 원문 부분어 누락 신호로 잡아 복합어 문서가 유의어 문서를 밀어냈다. 부정확한 관측 휴리스틱의 반례로 남긴다. 이 결과를 본 뒤 수정하면 새셋이 개발셋이 되므로 현재 점수를 유지했다.
- **V10 멀티텝, V11 악세사리:** 실제 분석은 단일 토큰이다. 작성한 `garbage_split` 가설이 관측과 맞지 않는다. 0/3을 실제 분해 오류 진단 성능으로 해석할 수 없다.
- **V12 피펫트:** 피펫/트로 분석되지만 N012는 이미 검색 1위이다. 분해가 있다고 실패라고 단정할 수 없다.
- **V15 차단제:** 현재 분석기에서 해당 상품이 이미 1위다. 복합어 실패라는 가설을 입증하지 못했고 무힌트 검색 적중도 실패했다.
- **H11 크림:** 개발 자료에서도 복합어 가설을 뒷받침할 토큰 누락 신호를 찾지 못했다. 무힌트 근거 검색 실패를 유지한다.
- **V08 육각 스패너↔육각 렌치**, **V13 전등의 N004/N013 관련도**에는 작성 정답의 의미적 모호성이 있다. V13의 N004 설명에도 전등이 있지만 정답은 N013만 지정했다. 이를 사후에 유리하게 고치지 않았다. 독립 인간 정답 검토 전에는 확정적인 품질 수치로 사용하면 안 된다.

후속 실험은 가설 오류·정답 모호성을 정리한 별도의 사전 고정 자료가 필요하다. 원래 가설을 그대로 따르는 모델도 적절한 진단으로 자동 인정하지 않는다.

## 2. 남은 검색 실패의 수정

기본 검색기 자체는 변경하지 않고 운영자가 지정한 후보를 별도 엔진에서 평가했다. v1의 아답터·백팩 두 연결이 적용된 설정을 비교 기준으로 삼았다.

| 개발 질의 | 추가 수동 후보 | nDCG@10 전 → 후 | 판정 |
|---|---|---|---|
| 거실 카페트 | 카페트↔카펫 | 0.8262 → **1.0000** | 기존36+v1정답있는20 게이트 통과 |
| 초콜렛 선물 | 초콜렛↔초콜릿 | 0.4582 → **0.9832** | 같은 게이트 통과, 완전 해결 아님 |
| 워시 | 바디워시→바디+워시 | 0 → **1.0000** | 같은 게이트 통과 |

카페트는 카펫 문서 중 거실이라는 부분 일치로 한 건만 찾았고, 초콜렛은 선물 토큰만 매칭돼 향초가 앞섰다. 워시는 원문 바디워시가 있지만 부분어 토큰이 없었다. 초콜렛 수정 후에도 P105 향초가 3위에 남고 P007이 뒤로 밀린다. 모든 후보의 전후 순위·점수·판정은 `development_repairs.individual`에 있다.

결합 설정: 기존36 평균 **0.6395→0.6950**, v1개발20 평균 **0.9142→0.9992**, 측정한 nDCG/recall/고정분모P@5 하락 0건. 개별 게이트의 precision5는 반환 결과 수 분모이므로 고정분모P@5와 별도 필드로 기록한다. 기존36의 다른 실패 질의는 여전히 남는다.

새 상품의 정답있는18질의에는 같은 설정을 그대로 적용했다. 평균 **0.5351→0.5351**, 개선0·하락0이었다. 수동 사전 변경이 새 표기와 의미를 자동으로 해결하지는 못했다. 관련 문서 없는6개는 평균에서 제외하며, V21은 무관한 N005가 검색됐다. 검색 결과 유무를 모델의 보류 성공으로 계산하지 않는다.

기존 A01의 변경된 인용, A09의 제목 인용, A05의 잘못된 복합어, A07의 백팩 원인 분류, A12의 상태 모순은 원응답에 그대로 남는다. 현재 프롬프트에 제목 인용 금지·복합어 재구성·힌트 반박·정상/범위밖 보류 규칙을 보강했지만 실제 모델의 재발 감소는 미실행이다. 직접 Prescription 경로의 탭/줄바꿈 우회를 재현해 막았다. K007의 편집 거리와 유사도 혼동 문구도 바로잡았으며 과거 제공 문서 스냅샷은 변경하지 않았다.

## 3. 설명·실제 LLM 평가 준비

[실행 계획](PAID-EVALUATION-PROPOSAL.md)과 [고정 입력 24개](llm-prepared-v1/requests.json)를 준비했다. 정상3·불명2·근거부족2·범위밖2를 포함한 전체24 중, 5계열 각1개+정상2+불명1+근거부족2+범위밖2=12개를 두 조건에서 호출할 계획이다. 근거 부족2개는 두 조건 모두 문서를 제거했다.

원인 분류(가설 라벨 일치), 인용 추적, 의미적 지지, 수정 구조, 실제 검색 효과를 분리한다. 오류·invalid를 정상 보류로 세지 않는다. 보류 요구 사례의 패치 시도는 원응답 기준으로 따로 기록하고, 실행 가능한 후보는 새 카탈로그 전체 정답있는18질의에서 별도 게이트로 평가한다. 일반 원칙 인용이 이번 원인과 연결되는지, 보류의 이유가 적절한지는 [독립 인간 검토표](llm-prepared-v1/human-review.json)에 빈칸으로 남겼다.

기존 실제 생성24응답을 현재 검증기로 감사한 상태는 **supported6 / abstain12 / invalid6**, 독립 인간 의미 평가 대기24건으로 동일했다. 이 과거 응답을 새 입력에 대한 모델 응답으로 사용하지 않았다.

## 4. 독립성과 범위

자료·정답은 Codex가 직접 작성했다. 관련도는 제목·설명과 의도한 요청을 읽고 특정 문서를2, 미지정 문서를0으로 정했다. 독립 사람의 판정은 없으며 위 모호성도 발견됐다.

기존 자료와 질의 문자열·상품ID·전체 상품 제목 중복0. 새 카탈로그 분석 어휘93개 중 **15개(16.13%)**는 기존 어휘와 겹친다. 공백 기준 공유 어휘는 led·usb·랜턴·케이스·휴대용이다. LED/USB 관련 상품 개념도 완전히 새롭지 않다. 같은 작성자, 한국어 상품 도메인, 운영 지식과 계열 분류를 공유하므로 독립 고객 일반화를 주장하지 않는다. 상세 교집합은 원자료 `novelty`에 있다.

## 최종 코드 리뷰

별도 AI 코드 리뷰에서 승인 준비물의 폴더를 복사하면 같은 승인으로 두 캠페인을 실행할 수 있는 허점을 공급자 대역으로 확인했다(실제 API0회). 준비물 해시 기준의 공통 실행 기록·예산 원장으로 바꾸고, 부분 실행 후 복사본 재시도를 차단하는 테스트를 실패→통과로 검증했다. 원장은 현재 체크아웃에 지속되며 삭제하거나 다른 체크아웃으로 옮기는 것을 계정 수준에서 강제 제한하지는 않는다.

실제 LLM 진단·보류, 인간 의미/정답 판정, 고객 일반화, 공급자 신뢰성, 공개 가용성은 코드 리뷰로 확인할 수 없으므로 미검증 상태를 유지한다. 리뷰 후 검색 알고리즘이나 고정 평가 정답은 변경하지 않았다. 재실행한 개발/새 검색·순위·이전 응답 감사의 모든 평가 값은 첫 기록과 같았다([재현 확인](checks/reproduction.json)).
